Build context:

  • Host: real POWER8 silicon, PVR 004b 0201 (v2.1, "Murano"), 4.157 GHz clock, 512 MHz timebase. KVM-virtualized as a single-core pSeries guest. The /proc/cpuinfo "emulated by qemu" string refers to the firmware/machine model that KVM-on-Power uses for guests, not to user-mode CPU emulation.
  • OS: Ubuntu 20.04 ppc64le.
  • Toolchain: IBM Advance Toolchain 15.0 (GCC 11.4.1) under /opt/at15.0/bin, Python 3.13.13 from a miniforge install, CMake 4.3.2 + Ninja from pip.
  • Build: standard scikit-build-core flow with CC=/opt/at15.0/bin/gcc CXX=/opt/at15.0/bin/g++, -O3 default. 4 GiB swap added because compiling the Farrar templates with -O3 exceeds the 1 GiB RAM during instantiation.

Parasail status:

  • Not built. Upstream parasail does not ship ppc64le wheels and a source build was not attempted in this pass. All ratios below are against generic on the same machine.

Power8 VSX semantic notes that drove the implementation

  • Lane numbering on Linux ppc64le is little-endian. The GCC altivec builtins largely hide BE register semantics, but vec_sld still exposes the BE Programming Interface Manual model: vec_sld(zero, v, 14) on the i16 lane shape is not "shift left by 1 lane". Cross-lane shifts use vec_perm with explicit LE-natural byte indices so the shift helpers match the SSE/NEON/LSX semantics one-to-one.
  • An early bug in shift_left_perm: the low half of the permutation was a constant 16 instead of 16 + i. This collapsed multi-byte inserted values (e.g. set1(low_score)) to byte 0 of the splat, dropping the upper bytes of the inserted scalar. Symptom: NW global lazy-F prefix carry produced wrong scores at widths 16/32 (correct at width 8 because byte 0 was the whole value there). Fixed by using 16 + i for the inserted indices.
  • vec_max for __vector signed long long is a Power9 (ISA 3.0) instruction. On Power8 the SimdOps<uint64_t, int64_t>::max is synthesized via vec_cmpgt + vec_sel over the 2 lanes.
  • vec_sel requires the per-width __vector __bool char/short/int/long long mask. The previous backend cast every comparison result to __vector unsigned char, which only happens to work for 8-bit lanes and was one source of the existing build break.
  • vec_cmpgt for signed long long requires ISA 2.07, which is Power8, so the 64-bit width has real SIMD comparisons.
  • Power8 has vbpermq (vector bit permute quadword). With control bytes [127, 119, ..., 15, 7] it collapses a per-byte 0xFF/0x00 mask into a 16-bit LE-natural lane bitmap in one instruction. Profiling showed the trace-mask step is only ~4% of the masked-traceback runtime on 1024x1024 English, so SimdOps::trace_mask_eq/gt uses a simple vector store + scalar fan-out instead. The vbpermq route is documented inline for a future micro-optimization pass.
  • vec_xl(0, uint64_t*) overload resolution picked the 32-bit-lane variant under GCC 11.4. Explicit cast to unsigned long long* forces the right one. Same story for vec_vsx_st against int64_t*.

Routing decisions that differ from x86_avx2 / Loongson

  1. Linear SW path / path-info / cigar stay on profile_traceback. The shared dispatch_linear_sw_score_first_masked_cigar_* path was wired up first (mirroring AVX2 and LSX) but measured 0.46-0.48x of the scalar byte-table path on 1024x1024 English. Profiling pointed at the striped trace table's poor cache locality on the traceback walk, not at the mask extraction. Reverted to profile_traceback and kept the helper hooks (trace_mask_*, mask_or, store_masked_cells) in SimdOps so any future redesign can reuse them.
  2. Affine SW / NW path / path-info also stay on profile_traceback. dispatch_affine_striped_path_info measured 0.57-0.60x for the same reason. Affine CIGAR stays on the SIMD score kernel + profile_traceback::affine_cigar_with_score because it skips the trace table entirely; that route still beats _generic by ~2x on sw-cigar and nw-cigar rows in this sweep.
  3. Linear SW / NW score, batch (1:many) score, affine score (compact byte), and prepared score profiles all route through the shared Farrar fixed kernel via the new SimdOps. These are the big wins.

Recommended Power8 next steps

  1. Try the vbpermq trace-mask fast path on real hardware to see whether the masked SW/affine traceback becomes competitive once mask extraction is one instruction. The other component of the gap is trace-table layout, which vbpermq does not address.
  2. Consider a Power8-specific linear SW trace redesign that keeps the byte trace table row-major (matching profile_traceback's layout) but uses VSX for the score DP only. This mirrors the affine CIGAR route that already beats generic by 2-4x.
  3. Add a Power8 local_affine_score_exact_segment128/256_raw mirroring the NEON local_affine_score_exact_fill_i16_128/i32_256 helpers, if the 1024-character query shape becomes a target. Score-only is already ~7-8x ahead of generic; the marginal win is small.
  4. Re-bench on a multi-core / non-virtualized Power8 host. This run was on a single-core KVM guest; SMT throughput and shared L2/L3 behavior on a physical 8-core / SMT8 chip are not represented here.
  5. Build parasail from source for ppc64le and re-run with a parasail column to mirror the format used by the x86 and macOS sweeps.
  6. Investigate why SWAR loses to generic on Power8. AT15 GCC 11.4 appears to auto-vectorize the generic score loops well enough that the 64-bit packed SWAR lanes give no benefit, but this is worth confirming with an asm dump rather than just timing.
